PM-TraitBench: a synthetic PM behavioural trait dataset

Brief for review, 2026-09-16. A frozen synthetic corpus of portfolio managers (PMs), their trade ledgers, their conversations with a copilot, and probes with ground truth, for evaluating the copilot's behavioural memory. Everything is generated offline; nothing waits on the live copilot.

1. Core concepts

Blue is visible to the system under test, red is hidden ground truth. Probe checkpoints are placed relative to each PM's own drift dates and regime boundaries. Full data model in Appendix B.

Three objects carry behaviour. Rules are every commitment the PM is held to, from the mandate (position cap) or from the PM (stop, trim, no adding before a trigger, exclusions, and per-idea stops, targets, and signposts). They are P&L-material and never breached by design; they are the reference against which biases are observed. Traits are what the memory system must learn, in one shape with a kind field: biases (P&L-material breaches of a rule or of a rational baseline; the copilot should counteract them) and preferences (not P&L-material; the copilot should comply). Signals, probes, and drift events reference trait_id only, so nothing the system reads says which kind a trait is.

2. The one design rule

A deterministic behaviour engine produces the ledger from the planted parameters; a language model only narrates the conversation around decisions already made. Persona prompting cannot be trusted to express planted biases (Z. Li et al., 2026; Yee & Koh, 2026). So the ground truth for each PM is the set of planted numbers and the trades the engine wrote from them. A sentence in a transcript is never ground truth; it is only narration of a decision the engine already made.

Drift events (half of PMs)

Three event types, dated per PM inside sampled windows so they never coincide with a regime boundary for the whole population: update (a bias attenuates after coaching, or a preference value is replaced; the old value becomes a probe distractor), dormant (a bias stops expressing), revive.

4. Market

  • Synthetic, abstract instruments; 52 weeks of daily data, 2026-01-05 to 2027-01-03. No memorised history for any model to lean on.
  • Four asset classes, 25% of PMs each: equities, rates and credit, commodities, multi-asset. One engine, one rule table, four expression adapters (instrument, risk unit, loss reference, anchor, consensus source).
  • Three seeds with the same instruments and different regime orderings; each PM lives in one seed.

5. Generation pipeline

  1. Sample personas, rules, traits, drift events. Deterministic; text fields from a reviewed template bank.
  2. Market, deterministic, one run per seed. Each regime is a parameter set (drift, volatility, cross-family correlation, mean reversion) switched on the seed's dates. Equities: factor model with moments matched to published statistics. Rates: two-factor level and slope per curve. Credit: rating-based spread plus a risk-off factor plus issuer noise. Commodities: spot plus a regime-dependent futures curve so roll yield exists. Range regime mean-reverts around round levels so anchoring has something to express. Consensus series follow lagged moves with scripted flips so herding has a signal to follow. Calendar events carry a scripted price effect and a label that signposts can key on.
  3. Engine: daily loop per PM; ideas are structured objects with machine-evaluable signposts; the engine fires triggers, logs the PM's response, applies bias parameters, writes the ledger with provenance. Deterministic.
  4. Gate 1: can the planted biases be read off the ledger alone, per asset class? Each bias is a rate over opportunity events (triggers, adds at a loss, consensus flips, exits near an anchor). A neutral dry run first confirms every seed and asset class yields enough events (about 7 to 30 per PM-year) for a planted rate to sit clear of neutral noise. Fix or drop any bias that fails, before any model is called.
  5. Plan signals: which trait shows in which session, stated or revealed, plus contradictions, retractions, third-party distractors, and a silence set of pure factual sessions. Sessions are event-driven, not weekly.
  6. Dialogue: the only high-volume model loop. A PM narrator (sees today's decisions and a one-line stance, never a number) and a simulated advisor (the real copilot's system prompt, market data via function calls, no persona access) alternate for 2-8 turns with structured output.
  7. Validate: leakage (no bias nameable from the text), ledger consistency (checked on a structured mentions field, not prose), forbidden traits (two-model judge with logged agreement). Failures regenerate.
  8. Gate 2: a strong model with full context recovers each trait from dialogue alone; that is the ceiling any memory system can reach.
  9. Probes generated from ground truth; answer keys fixed before any paraphrase.
  10. Freeze: hashes, README with every guessed setting, model ids, pass rates.

6. Probes

Checkpoints are relative to each PM: week 4, week 13, before and four weeks after each drift event, after each regime boundary, week 52. Context for a probe is every session up to the checkpoint. No probe asks for a number.

TypeWhat it asksScoring
Trait presenceyes/no per trait; negatives include inactive biases, unexpressed preferences, and traits stated only by a colleaguedeterministic
Trait MCQa live situation; options are the engine's actions under the current value, the pre-update value, the self-image, and a third party's valuedeterministic
In-situ responsePM asks the copilot to act or advise; comply with a preference, counteract a bias and name it, decline a mandate breachLLM judge
Routine questiona factual question; format must follow the PM's communication preferences and no bias content may intrudedeterministic format, LLM judge for intrusion
Governancea query whose premise assumes the pre-update value; must be resistedLLM judge

Every LLM-judged score is checked against a human-rated sample in the pilot and the agreement rate reported. Every result is reported split by whether the supporting evidence was stated or revealed.

Per PM: 55-80 sessions, about 65-100k tokens of history, driven by the signal plan (about 3 active biases at 8-10 carrier sessions each, 4-8 preferences at 3 each, distractors, and filler so that signal-carrying sessions stay under 40%). Roughly 9-16M output tokens for the full build. Ledgers, ideas, and probes cost no model tokens.

Appendix B: data model

Crow's foot notation: bar = exactly one, circle = zero, crow's foot = many. Hidden ground truth never shown to the system under test: traits, drift_events, signals, probes, and bias_flag on the ledger.
