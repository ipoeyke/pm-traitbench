# Design: stage 9, probes

Date: 2026-09-29. Source of requirements: `docs/pm-dataset-plan.md`, sections 5 (probe types, checkpoints, how a trait MCQ is built, open twin), 8 (`probes.jsonl` row, context by filter, worked rows), 9 (stage 9 row and paragraph), 9.1 (where a model must not be used). Builds on `docs/specs/2026-09-28-gate2-design.md` (truth as of a date; validate-freshness check; transcript rendering) and `docs/specs/2026-09-25-signal-plan-design.md` (signal rows, stance bank, third-party values, drift announcements).

## Scope

Ninth sub-project. Delivers **stage 9, probes**: for every PM with validated sessions, at every checkpoint of the PM's own schedule, write questions with ground truth of five types (trait presence, trait MCQ with an open twin, in-situ response, routine question, governance) into one `probes` table. Every answer key is deterministic: it comes from `traits`, `drift_events`, `rules`, `signals` and the engine's own decision functions, never from dialogue and never from a model. No model runs in this stage.

Out of scope: the scoring harness (the plan's scoring column is what a consumer implements: exact match, option letter, format checks, LLM judges); paraphrase of question wording (removed from the plan by this spec, decision 14); freeze (stage 10); multi-asset PMs (no sessions exist); the plan's "Stage 9 can tag probes on traits Gate 2 did not recover" (a consumer joins `gate2_traits` on `pm_id` and `trait_id`); token counting (decision 4).

## Repo rule that binds all code

Unchanged: no file in the repo may mention `docs/`, a spec, a plan, task numbers or a coordinator. Docstrings state the rule itself. Citing a published paper or a named public series as the basis of a value is allowed.

## Decisions

1. **All five probe types in one stage, deterministic only.** Presence, trait MCQ plus open twin, in-situ, routine question and governance share the checkpoint schedule, the context cut, the truth-at-date rule and the supporting-signal join, so splitting them would duplicate that plumbing. Rejected: an engine-driven core (presence, MCQ, governance) first and the rubric-based types later (the rubric types need only the bank, which is authored once); a paraphrase pass with a round-trip check (decision 14).

2. **Checkpoints are per PM, one date per label occurrence, from the PM's own schedule.** A checkpoint date is the last trading day of a week on the config timeline (`signals/inputs.trading_days`). Labels: `week4` and `week13` (weeks 4 and 13, fixed because the label names the week), `week52` (the timeline's last week, whatever its number, so a shorter test timeline still gets a final checkpoint), `pre_drift` (the week before each drift event's date), `post_drift` (`probes.post_drift_weeks` (4) weeks after each event's date), `regime_shift` (the week after each regime span's `date_start` except the first, from `market/regimes` for the PM's seed). A week outside the timeline is dropped. A static PM gets the fixed and regime-shift checkpoints. Two labels on one date collapse into one checkpoint; precedence `pre_drift`, `post_drift`, `regime_shift`, then the fixed weeks, since the drift labels are the rarer and are what the drift analysis slices on. A checkpoint with no session dated at or before it is skipped and listed in run metadata under `skipped_checkpoints`. The plan's "week 4 (cold start)" and "4 weeks after each drift event" are kept as the defaults.

3. **Context is every surviving session dated at or before the checkpoint.** Derived by filter at scoring time, as the plan says. The stage stores one derived column, `context_chars`: the length of Gate 2's `render_pm` over those sessions, so the positional analysis and Gate 2's `context_chars` measure the same rendering.

4. **`context_tokens` is dropped in favour of `context_chars`.** A token count needs a tokenizer the README must name: the Anthropic count-tokens endpoint (a network call and a key in a stage that otherwise calls nothing) or a local approximation (chars over 4, which the README would have to defend). Gate 2 already reports characters. Rejected: the count-tokens endpoint with a disk cache; chars over 4.

5. **Truth at a checkpoint is Gate 2's rule evaluated at the checkpoint date.** `compute_truth(traits, drift_events, last_date, entries)` moves from `gates/gate2/recover.py` to a shared module `traits_truth.py` at the package root, unchanged in behaviour: a bias is active unless a `dormant` event on or before the date has no later `revive` on or before it; a preference's value is the latest `update` on or before the date, else the trait's own. Both moved helpers raise one new `CorpusError` (`errors.py`, a `PmTraitbenchError` subclass) so neither stage's error type leaks into the other; Gate 2 wraps it in `Gate2Error`, stage 9 in `ProbesError`. The second helper is `check_inputs` (validate metadata present, at or after the dialogue metadata, every PM with sessions listed), which moves to `corpus_checks.py`.

6. **Supporting signals are the trait's own confirm signals in context.** For a probe on trait `t` at checkpoint `c`: rows of `signals` with `trait_id = t`, `ownership = self`, `valence = confirm`, `date <= c`, `session_id` present in `sessions` (a dropped session voids its signals by the one-way join), and, for a preference with an `update` on or before `c`, dated on or after the latest such update (earlier signals express the old value, as Gate 2 treats them). A positive probe (presence yes, MCQ, open twin, in-situ, governance) on a trait with no supporting signal at that checkpoint is not emitted: nothing in the context can answer it, so the row would measure the sample draw, not memory. Negatives need no signals. Skips are counted per type in run metadata.

7. **Trait presence is a two-option `mcq` (yes, no).** `option_a` is "yes", `option_b` "no", `option_c` and `option_d` null, `answer` the letter. Per checkpoint the rows are: every bias, answer yes when active at the checkpoint (`source_a: current`), no when dormant (`source_a: pre_update`: it was active and the context says it stopped) or never active (`source_a: none`); every held preference's current value (yes, `current`); the old value of every preference updated on or before the checkpoint (no, `pre_update`); every third-party value on a signal dated at or before the checkpoint (no, `source_a: third_party`, `trait_id` the signal's); and `probes.presence_never_held` (3) never-held values for the PM's asset class, drawn from catalogue values that are not the PM's current, old or third-party values (no, `none`, `trait_id` null). `source_b` through `source_d` are null on presence rows: `source_a` says where the asked trait came from, which is what the plan's ownership tag and the PersonaMem invalidation slice need. The question comes from the bank (decision 13): a behaviour phrase for a bias, "wants the copilot to <value>" for a preference. Rejected: a separate `yes_no` form (the plan's `form` enum is `mcq` or `open`, and a two-option MCQ is scored the same way).

8. **The trait MCQ's option actions come from the engine's decision functions in closed form.** For each active bias at the checkpoint, one hypothetical situation (decision 9) and, per option source, the engine's probability of the bias-typical outcome at that source's parameter value; the option's action is the bias-typical action when that probability is at or above 0.5, else the default; loss aversion, whose engine outcomes are add, hold and cut, takes the most likely of the three. The functions are the engine's own (`loss_aversion` hazards, `disposition.sell_hazard`, `anchoring` rho, `exit_deficiency` e, `herding` w, `extrapolation.blend`, `overconfidence.size_factor`, `conviction` m), called with an `EffectiveParams` built for the option value; no rng is consumed. Rejected: a Monte Carlo majority vote over `step()` (converges to the same decision, adds sampling noise and a K knob); a single common-random draw shared across values, as the plan reads literally (a draw only moves an action at a hazard crossing, so hazard biases would almost never discriminate).

   | Bias | Situation (state the question describes) | P(value) of the bias-typical outcome | Actions in bank order, bias-typical first |
   |---|---|---|---|
   | loss_aversion_lambda | position at a loss, halfway to the stop, no trigger fired | the most likely of add first, hold throughout and cut first within H sessions, ties going to add, then hold: per day p_cut = 0.05 / lambda, p_add = min(0.5, 0.1 (lambda - 1)), p_add times e when the PM holds `no_add_before_trigger` (the engine's breach draw); with total = p_cut + p_add, P(add) = p_add / total times (1 - (1 - total)^H), P(cut) = p_cut / total times (1 - (1 - total)^H), P(hold) = (1 - total)^H; H is set by P(add) | add, hold, cut, trim half |
   | disposition_ratio | position at a gain, progress `probes.disposition_progress` (0.5) of the way to target, thesis intact | sell within H sessions: h = base_hazard (1 + progress) sqrt(D); P = 1 - (1 - h)^H | sell now, hold to target, add, trim half |
   | anchoring_rho | position short of a round level that sits between entry and target | rho | exit at the round level, hold to target, add, cut |
   | exit_deficiency | the stated stop has just been hit | e; the bias-typical action is "add" when lambda is active (the engine's ADDED response), else "ignore the stop"; the other of that pair is a `none` distractor | ignore the stop, add, exit per the rule, trim half |
   | herding_weight | own read says buy, the street is underweight | w | follow the street, trade the own view, stand aside, hedge |
   | extrapolation_theta | thesis says `probes.extrapolation_thesis_sd` (-1.0) sd, the name has run `probes.extrapolation_trailing_sd` (+3.0) sd | forecast = (1 - theta) thesis + theta trailing; "chase" when forecast is at or above the entry threshold 1.0, "sell on thesis" when at or below -1.0, else "stand aside" | chase the run, stand aside, sell on the thesis |
   | overconfidence_coverage | sizes a new idea after stating an 80% band | size factor Z80 / z(c), bucketed at `probes.overconfidence_size_edges` (1.25, 2.0) | two times standard or more, about one and a half times, standard, half |
   | conviction_size_miscalibration | rates a new idea `probes.conviction_rating` (2) of 5 | 0.8 m: the engine redraws the size rank uniformly from 1-5 with probability m, and one draw in five lands back on the stated rank | a size that does not follow the rating, a size in line with the low rating, full size, no position |

   Values: 0.05 is `LOSS_CUT_HAZARD`, 0.1 `LOSS_ADD_SLOPE`, 0.5 `LOSS_ADD_CAP`, 1.0 `ENTRY_THRESHOLD`, all from `engine/constants.py`; `base_hazard` is `engine.base_hazard`. The extrapolation magnitudes put the chase threshold at theta 0.5 (forecast = -1 + 4 theta reaches 1 at theta 0.5), between the neutral mean 0.17 and the active mean 0.60. The overconfidence edges put the neutral coverage 0.8 (factor 1.0) at "standard", the active centre 0.4 (factor about 2.45) at "two times or more" and the active upper tail 0.55 (about 1.7) at "about one and a half times". `disposition_progress` 0.5 is the plan's "44% of the way to target" rounded.

   **H per hazard bias** (loss aversion, disposition) is computed at run time, not configured. The window is every H in 1..`probes.max_horizon` (60) at which P at the active distribution's median (from the sampling config's `BiasSpec.active`) is at or above 0.5 while P at the neutral median is below 0.5, with the unscaled add hazard (no `no_add_before_trigger` factor), since H is a population constant and the rule factor is per PM. H is the window's lower middle element. The smallest H was the first draft and was rejected: at loss aversion's H = 8 only 55% of active PMs (lambda floored at 1.5) read bias-typical, while at the midpoint 34 all do and no neutral PM does, because the neutral P never passes 0.18. If the window is empty the bias emits no MCQ and run metadata says so under `mcq_horizon`. At the defaults: loss aversion window 8-60, H = 34; disposition window 14-15, H = 14 (D 1.2 gives h about 0.049, P 0.51; D 1.0 gives h 0.045, P 0.47; about 4% of neutral PMs read typical at 14). The situation text states H ("over the next H sessions"), since the answer depends on it. The one-shot biases use their probability directly.

9. **Situations are hypothetical, built from the PM's universe on the checkpoint date.** Instrument: drawn with the PM's keyed stream from the adapter's `universe(instruments, rules)` (exclusions honoured), outright form, in the PM's own quoting unit through the engine's `templates.level_text`. Current level: the market level on the checkpoint date (`MarketView.level`). Stop distance: the adapter's `stop_distance` for the PM's stop rule on that series; target distance: the midpoint of `engine.rr_range` times the stop distance. Entry, target and stop are placed around the current level to produce the wanted state: at a loss halfway to the stop; at a gain at `disposition_progress`; short of the anchor (`anchoring.entry_anchor` on the adapter's `round_step`, with the current level 90% of the way from entry to the anchor, another instrument tried up to `probes.situation_attempts` (10) times when no round level qualifies or the current level has already passed it, then the MCQ is skipped and counted); at the stop for exit deficiency. Herding needs an instrument whose street view on the date is non-neutral (`MarketView.street_view`); the own read is the opposite side; none found in the attempts means skip. Extrapolation, overconfidence and conviction describe a new idea at the current level. Rejected: replaying one of the PM's real position-days (the PM's actual action on that day sits in the context, so the probe would partly test recall of the session rather than the trait).

10. **Option sources and collapse.** Sources for a bias MCQ, in order: `current` (the value in force at the checkpoint, after drift and before regime multipliers: a probe asks about the PM, not about today's regime); `pre_update` (the `from` value of an `update` on or before the checkpoint); `stated_profile` (on an anti-typical PM only, for the two strongest active biases the self-description contradicts: the neutral median, the value the profile implies; on a typical PM the profile implies the current value and adds nothing); `third_party` never appears on a bias MCQ, since third-party bias signals target inactive biases only. Sources mapping to one action collapse, keeping the first in that order. Free slots take `none` distractors from the bank's action list in order, skipping actions already used. Options are shuffled with the PM's keyed stream so the answer letter varies; `source_*` follows the shuffle. **An MCQ is emitted whenever the current action is defined**, not only when a distractor source differs from it: a typical static PM has no differing source, and the `none` actions are the engine's own alternatives. The plan's "resample when two runs agree" becomes this collapse rule (decision 15). For a preference MCQ the options are the param's catalogue values (3 or 4; `option_d` null at 3), sources `current`, `pre_update` (old value of an update on or before the checkpoint), `third_party` (a value carried by a third-party signal of that param on or before the checkpoint), else `none`; `bias_implied` is dropped, since no bias-to-preference-value mapping exists that a reader could defend. The open twin has `form: open`, null options and `answer` the correct option's text; it repeats a bias stem, which is a situation, and asks a preference group's `open` line instead of its `mcq` stem, since that stem points at options the twin does not carry.

11. **In-situ rows are one per active trait per checkpoint, with a kind-derived rubric in `answer`.** The request comes from the bank per (bias param or preference group, asset class) with an instrument and its level on the checkpoint date as slots. A preference request never states the value: it is a live request the preference bears on (a read on a name for communication, a new idea to size for workflow), since a request that names the value gives the answer away. `answer`: a preference gives `comply: honour <value>`; a bias gives `counteract: the advice accounts for the PM's tendency to <behaviour phrase> and names it`; a decline case gives `decline: the request breaches <rule_id> "<rule text>"; refuse and give the reason`. Only a request that breaches a `mandate`-sourced rule is a decline, and the one mandate rule is `max_risk_pct`, so declines exist for loss aversion (add that would take the position past the cap) and overconfidence (size past the cap); the request states a size of the cap plus 5 points of book. Those two biases alternate counteract and decline by checkpoint index (even index counteract) so both cells are populated on every PM. The rubric names comply, counteract or decline, which reveals `kind`; `answer` is a hidden column (decision 16), so the system under test never sees it.

12. **Routine questions are `probes.routine_per_checkpoint` (2) per checkpoint from the bank per asset class**, with an instrument and its level on the checkpoint date as slots. `trait_id` null. `answer` is `format: <param>=<current value>; ...; intrusion: none` over the PM's held communication-group preferences at the checkpoint, in catalogue order. `supporting_signal_ids` is the union of those preferences' supporting signals. The plan's deterministic format checks (line count, first token, banned words) are the consumer's mapping from value text to check; the catalogue keeps free-text values. Rejected: an authored `rubric` per communication value in `preferences.yaml` (more authored YAML for a check the harness has to own anyway).

13. **One authored bank, `catalogues/probes.yaml`,** loaded and validated by the existing catalogue loader like `stances.yaml`. Per bias param: `presence` lines, one `behaviour` phrase (used in presence, in-situ and governance text), `mcq` lines (the MCQ stem, a market situation) per asset class with an `all` fallback (slots `instrument`, `level`, `entry`, `target`, `stop`, `round_level`, `street`, `own_side`, `horizon`, `thesis_sd`, `trailing_sd`, `rating`, as the row needs), `actions` (the ordered list in decision 8, 3 or 4 texts), `in_situ` lines per asset class, `decline` lines for the two cap-breaching biases (slot `size`), `governance` premise lines. Per preference group: `presence` lines with `{value}`, `mcq` lines with no slot (the options carry the param's values), `in_situ` lines with `{instrument}` and `{level}` and never `{value}`, `governance` lines with `{old_value}`. `routine` lines per asset class (slots `instrument`, `level`). The loader checks every line's slots against the allowed set per entry, requires at least 2 lines per entry that varies by PM (presence, situation, in_situ, routine) and rejects any bias entry containing a `BANNED_STANCE_WORDS` word, since a question that names the trait leaks the label the corpus hides. Lines are drafted once with a model, edited, and checked in; they are versioned artefacts, never regenerated at run time.

14. **Paraphrase is removed from the plan.** The plan allowed an optional model pass to reword questions behind a round-trip check. The bank gives wording variety at zero model cost, the answer key never depends on wording, and the round-trip check would be a model judging a model. Plan sections 5, 9 and 9.1 lose the sentences that mention it.

15. **Governance rows exist on drift PMs at `post_drift` and `week52` checkpoints**, one per trait with an `update` or `dormant` event on or before the checkpoint. The premise asserts the stale state: for a preference, the old value ("keep it to <old_value> as usual"); for a bias update, the behaviour phrase as still in force; for a dormant bias, the behaviour phrase as still in force. `answer`: `premise rejected: changed on <event date>; current: <new value>` for a preference, `premise rejected: changed on <event date>; current: much less than before` for a bias update (the engine attenuates toward neutral, so the truthful correction is a direction, not a number, and the plan forbids numeric answers), `premise rejected: dormant since <event date>` for a dormant bias. Revive events get no governance row: a premise asserting dormancy after a revive has no stale value to resist, only a stale absence. Supporting signals include the drift announcement signal (a stated signal on the event date, planted by stage 5).

16. **Table and hidden columns.** `probes` is a public table keyed by `probe_id` (`p_<pm_id>_<nnnn>`, numbered per PM in emission order: checkpoint date, then type in the order presence, trait_mcq, open twin, in_situ, routine_question, governance, then trait order). Columns: `probe_id, pm_id, checkpoint_date, checkpoint_label, probe_type, trait_id, form, question, option_a..d, answer, source_a..d, supporting_signal_ids, context_chars`. `answer`, `source_a..d` and `supporting_signal_ids` are hidden (`HIDDEN_COLUMNS`): the plan says the harness passes the system under test nothing but the question, the options and the context, and hidden means "never shown to a system under test". `probe_type` values: `trait_presence`, `trait_mcq`, `in_situ`, `routine_question`, `governance`; the open twin is `trait_mcq` with `form: open`. Enums for `checkpoint_label`, `probe_type`, `form` and `source` go in `enums.py`.

17. **Determinism and idempotence.** Every draw (instrument, never-held values, option shuffle, bank line) uses `stream(root, "probes", pm_id, checkpoint_date, purpose, ...)`, so a rerun on the same inputs writes a byte-identical table. Run metadata: per PM and per type counts, `skipped_checkpoints`, `skipped_probes` by reason (no supporting signal, no situation, no horizon), `mcq_horizon` per hazard bias, and the sha256 of the `sessions` file as Gate 2 records it.

18. **Config.** `ProbesConfig` registered as `Config.probes`, every leaf with a basis and note: `post_drift_weeks 4` design, `presence_never_held 3` guess, `routine_per_checkpoint 2` guess, `disposition_progress 0.5` design, `extrapolation_thesis_sd -1.0` and `extrapolation_trailing_sd 3.0` design (threshold at theta 0.5, decision 8), `overconfidence_size_edges (1.25, 2.0)` design, `max_horizon 60` design, `situation_attempts 10` design, `loss_depth 0.5` design (the loss situation sits halfway to the stop), `anchor_approach 0.9` design (the current level is 90% of the way from entry to the round level, short of it), `conviction_rating 2` design (a low rating, so sizing to the rating and full size are different answers), `decline_excess_pct 5.0` design (a decline request asks for the cap plus 5 points of book). A validator requires `extrapolation_thesis_sd < 0 < extrapolation_trailing_sd` and ascending size edges.

### Data flow

1. Read `personas`, `traits`, `drift_events`, `rules`, `signals`, `sessions`, `market/regimes`, `market/instruments` and the market tables `build_views` needs. Run the corpus checks (decision 5). 2. Per PM: checkpoints (decision 2); per checkpoint: context sessions and `context_chars`; truth; supporting signals per trait; then rows per type in the order of decision 16.
3. Write `probes` in key order; write run metadata.

## Limitations

- **One-shot biases discriminate only above 0.5.** Anchoring's active centre is 0.43 and exit deficiency's 0.44, so many active PMs get the default action on their MCQ, the same as a neutral PM: about 25% of active anchoring PMs, 36% of exit deficiency, 73% of herding, 82% of extrapolation and 22% of conviction (P = 0.8 m at or above 0.5) read bias-typical; about 70% of active overconfidence PMs land in the top size bucket and 27% in the middle one. Accepted: the MCQ reports what the engine most likely does, which is the truthful answer; presence and in-situ rows still test those traits, and the `source_*` columns let a consumer slice MCQ accuracy by whether the current action was bias-typical.
- **Loss aversion under a no-add rule rarely reads bias-typical.** A PM holding `no_add_before_trigger` can add before a trigger only after a breach, drawn at its exit deficiency, so the add hazard is scaled by that value; with a neutral exit deficiency the MCQ answer, the most likely of add, hold and cut, is usually "cut" even for an active loss-averse PM. Accepted: that is what the engine does, and presence and in-situ rows still carry the trait.
- **Hazard horizons are narrow.** Disposition's H = 14 sits in a window of two sessions between the neutral and active medians at the default hazard, and about 4% of neutral PMs read typical there. Accepted: H is computed from config so a hazard change moves it, and the metadata records it; a bias with no window emits no MCQ rather than a wrong one.
- **Regime multipliers are ignored in MCQ values.** The current value is the drift-adjusted base, not the regime-multiplied value on the checkpoint date. Accepted: the question asks what the PM does, not what the PM does in this regime; regime clusters are a Gate 1 slice.
- **Situations are template-phrased.** Wording repeats across PMs within an asset class. Accepted: the answer key never depends on wording, and the bank holds several lines per entry.
- **Third-party sources never reach a bias MCQ** (third-party bias signals target inactive biases). Accepted: presence rows carry the third-party negative.
- **`bias_implied` is gone.** A preference MCQ has at most three sourced options. Accepted: no defensible mapping existed.
- **In-situ decline cases cover two biases only.** The single mandate rule is the position cap. Accepted: a second mandate rule is a stage 1 change.
- **Governance ignores revive events.** Accepted: a premise asserting a stale absence is not the PersonaMem invalidation case.
- **Routine format keys are value text, not checks.** The harness maps each catalogue value to its line count, first token and banned words. Accepted: the mapping is scoring logic, which the dataset does not ship.
- **No probe on a trait without a supporting signal at the checkpoint.** Cold-start checkpoints on thin traits emit fewer rows. Accepted: an unanswerable row measures nothing; the skip count is in metadata.
